# 六、部署运行手册

## 1. 环境要求

| 组件 | 版本要求 | 说明 |
|---|---|---|
| JDK | **17**（必须） | Spring Boot 3 的最低要求 |
| Maven | 3.8+ | 建议 3.9 |
| Node.js | 18+ | 建议 20 LTS（仅前端构建需要） |
| 数据库 | 无需安装 | 默认使用内置 H2 文件库；生产可换 MySQL 8 |
| 浏览器 | Chrome 100+ / Edge 100+ | 大屏建议 Chrome 全屏（F11） |

> **离线提示**：前端不依赖任何外部 CDN / Web 字体 / 图标库，
> 后端依赖走 Maven 坐标。内网部署时只需一次联网构建，之后可完全离线运行。

## 2. 快速启动（H2，零依赖，推荐先用这个跑通）

### 2.1 启动后端

Windows：

```bat
cd mes-max\backend
run.cmd
```

Linux / macOS：

```bash
cd mes-max/backend
mvn spring-boot:run
```

首次启动会自动完成三件事（日志中可看到）：

```
SQL 脚本命中：.../sql/schema.sql
建表脚本执行完成：48 条语句（7 ms）
空库检测通过，灌入 CNC 车间主数据：19 条语句（24 ms）
开始生成 CNC 车间演示流水（历史 14 天）…
演示流水生成完成：订单 36，工序任务 210，报工 238，耗时 1331 ms
设备采集模拟器已启动，纳管机床 12 台
Tomcat started on port 8080 (http) with context path '/api'
```

此时：

| 地址 | 用途 |
|---|---|
| `http://localhost:8080/api` | 后端接口根路径 |
| `http://localhost:8080/api/h2-console` | H2 数据库控制台（答辩现场查库演示用） |

H2 控制台登录参数：JDBC URL `jdbc:h2:file:./data/mesmax;MODE=MySQL;DATABASE_TO_LOWER=TRUE`，
用户 `sa`，密码 `mesmax`。

> ⚠️ **连接串是相对路径**：库文件落在「启动目录」的 `data/` 下 —— 从仓库根启动会写
> `mes-max/data/`，从 `backend/` 启动会写 `backend/data/`，两个目录互不相通
>（「明明灌了种子却查不到数据」多半就是这里）。启动日志里现在会打印实际连到的绝对路径：
>
> ```
> 数据库：H2 2.2.224 | jdbc:h2:file:D:/.../backend/data/mesmax
> ```
>
> 请固定从 `backend/` 启动（`run.cmd` / `run.sh` 已如此）。

> 两个安全默认值（都是刻意设置的，不要随手改回去）：
> ① 连接串**不开** `AUTO_SERVER` —— 那是允许本进程以外的其它 Java 进程连上同一个库文件的能力，演示场景不需要；
> ② H2 口令**不是空串** —— 空口令 + 放行的控制台，等于把整库交给任何能访问 8080 的人。
> 控制台只在 `h2` profile 下装配（`mysql` profile 不会开启），且 `web-allow-others: false`。
>
> ⚠️ H2 的库口令写在**文件头**：改了 `spring.datasource.password` 之后，
> 用旧口令建的 `data/` 会连不上（启动时报 Hikari 连接失败，程序会额外打印排查提示）。
> 处理办法三选一：删掉 `backend/data` 重建（演示环境最省事）、改回原口令、或改用 MySQL。

### 2.2 启动前端

```bash
cd mes-max/frontend
npm install
npm run dev
```

浏览器打开 `http://localhost:5173`（Vite 已配置 `/api` 代理到 8080，无需额外配置跨域）。

### 2.3 生产构建（部署到 Nginx）

```bash
cd mes-max/frontend
npm run build        # 产物在 dist/
```

将 `dist/` 拷到 Nginx 站点目录，并按 [nginx.conf](../frontend/nginx.conf) 配置反向代理。
**注意**：SSE 实时看板必须关闭代理缓冲（`proxy_buffering off`），否则大屏不会逐条刷新。

## 3. 使用 MySQL 8

### 3.1 建库建表

```sql
CREATE DATABASE mes_max DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci;
```

建表与种子脚本可手工执行（也可由程序自动执行）：

```bash
mysql -uroot -p mes_max < sql/schema.sql
mysql -uroot -p mes_max < sql/seed-data.sql
```

### 3.2 以 mysql profile 启动

```bash
cd backend
mvn spring-boot:run -Dspring-boot.run.profiles=mysql
```

或通过环境变量指定连接信息（推荐用于容器/服务器）：

| 环境变量 | 默认值 | 说明 |
|---|---|---|
| `MES_DB_HOST` | `localhost` | 数据库地址 |
| `MES_DB_PORT` | `3306` | 数据库端口 |
| `MES_DB_NAME` | `mes_max` | 库名 |
| `MES_DB_USER` | `root` | 用户名 |
| `MES_DB_PASSWORD` | `root` | 密码 |
| `MES_JWT_SECRET` | 未配置时**启动随机生成** | 建议显式配置（≥16 字符）。未配置时令牌在重启后失效、需要重新登录 |
| `MES_DEFAULT_PASSWORD` | `mes123456` | 新建账号 / 重置口令时使用的初始口令（不参与登录校验） |
| `MES_LOGIN_MAX_FAILURES` | `8` | 登录失败节流阈值（同一账号在窗口内失败次数） |
| `MES_LOGIN_FAILURE_WINDOW` | `300` | 登录失败节流窗口（秒） |
| `MES_CORS_ORIGINS` | 本机 5173 / 4173 | 允许跨域的来源白名单（逗号分隔）。同源部署（Vite 代理 / Nginx 反代）时用不到；留空 = 不开放跨域 |

```bash
export MES_DB_HOST=192.168.1.20 MES_DB_PASSWORD='Strong#Pwd' MES_JWT_SECRET="$(openssl rand -hex 32)"
mvn spring-boot:run -Dspring-boot.run.profiles=mysql
```

## 4. Docker 一键部署

```bash
cd mes-max
docker compose up -d --build
```

> 后端镜像的**构建上下文是项目根目录**（`context: .` + `dockerfile: backend/Dockerfile`），
> 因为镜像里要同时带上 `backend/` 源码和 `sql/` 建表脚本，而 `COPY` 不允许越出构建上下文。
> 手工构建等价命令：
> ```bash
> docker build -f backend/Dockerfile -t mes-max-backend .
> ```

| 服务 | 地址 |
|---|---|
| 前端 | `http://localhost:8888` |
| 后端 | `http://localhost:8080/api` |
| MySQL | `localhost:3307`（root / `mesmax@2026`） |

停止与清理：

```bash
docker compose down            # 停止容器（保留数据卷）
docker compose down -v         # 停止并删除数据库数据卷（会清空数据）
```

## 6. 数据重置与重新演示

演示一段时间后数据会变乱，需要回到干净初始状态：

```bash
# Windows
cd backend
set MES_RESET=-Dmesmax.db.reset=true && run.cmd

# Linux / macOS
cd backend
MES_RESET=-Dmesmax.db.reset=true ./run.cmd
```

启动时日志会显示：

```
检测到 mesmax.db.reset=true，正在清空数据库全部对象…
数据库已清空，将重新建表并灌入种子数据
```

因为演示流水使用固定随机种子（`20260921`），**每次重置后得到的数据完全相同**，
便于反复演示与回归测试。

## 7. 常见问题

| 现象 | 原因与处理 |
|---|---|
| 启动报 `Port 8080 was already in use` | 已有后端在运行。先停掉旧进程，或改 `server.port` |
| 启动报 `Could not find class [org.springframework.boot.thread.Threading]` | 依赖版本串味：`spring-boot-autoconfigure` 被解析成 4.x。本项目已在 `pom.xml` 中固定为 3.2.5 并排除传递依赖；若本地 `.m2` 有异常元数据，执行 `mvn -U clean compile` |
| 编译报 `Error reading old mojo status ... inputFiles.lst: Input length = 1` | Maven 状态文件编码不一致（Windows 中文路径 + GBK）。执行 `mvn clean compile`，或使用项目自带的 `run.cmd`（内部已设置 `-Dfile.encoding=UTF-8`） |
| 中文日志或中文路径乱码 | 用 `run.cmd` 启动，或在 `MAVEN_OPTS` 中加 `-Dfile.encoding=UTF-8` |
| 前端能打开但接口 404 | 确认后端已启动在 8080；Vite 开发模式检查 `vite.config.js` 中的代理配置 |
| 大屏数据不刷新 | SSE 被拦截：检查 Nginx 是否配置 `proxy_buffering off`；浏览器 F12 查看 `/api/board/stream` 连接状态 |
| 登录提示「服务未启动」 | 登录页左侧状态灯为红，说明探测 `/api/auth/login` 失败，后端没起来 |
| 换个数据库后启动报索引错误 | MySQL 8 不支持 `CREATE INDEX IF NOT EXISTS`，程序内部已对该类语句做容错跳过，属正常日志 |
| `npm install` 报 `EPERM / spawn` | 通常是被杀毒软件或权限策略拦截了 postinstall 脚本。可用 `npm install --ignore-scripts`（本项目前端依赖无需编译原生模块） |

## 9. 令牌密钥与「重启后是否需要重新登录」

后端解析签名密钥的顺序（实现见 `com.mesmax.common.JwtUtil.resolveSecret`）：

| 优先级 | 来源 | 适用场景 |
|---|---|---|
| 1 | 环境变量 `MES_JWT_SECRET` | 生产、多实例、容器部署（**应显式配置**，建议 `openssl rand -hex 32`） |
| 2 | 启动目录下的 `.jwt-secret` 文件 | 本机演示 / 答辩：文件存在则复用，**登录态跨重启依然有效** |
| 3 | 两者都没有 → 生成 32 字节随机密钥并写入 `.jwt-secret` | 首次启动自动完成，日志会打印密钥来源 |

**为什么不是「每次启动都随机」**：答辩现场经常重启后端，每次重启把所有在线的人踢下线是没必要的折腾。

**为什么不是「写一个固定默认值」**：一旦默认密钥进了代码或部署文件，任何人都能用它自签一个
`role=admin` 的令牌（甚至可以不带 `exp` 做成永久令牌），车间内网也一样能被攻破。
密钥文件 `.jwt-secret` 已加入 `.gitignore`，**不要提交**。

| 想做的事 | 操作 |
|---|---|
| 强制所有人重新登录 | 删除 `.jwt-secret` 后重启（容器里不挂载该文件即可） |
| 多实例共享登录态 | 给所有实例配置同一个 `MES_JWT_SECRET` |
| 换密钥存放位置 | 加启动参数 `-Dmesmax.jwt.secretFile=/etc/mes-max/secret` |

> ⚠️ **`.jwt-secret` 是相对路径，解析基准是「JVM 启动目录」**：
> 从 `backend/` 启动 → `backend/.jwt-secret`；从项目根执行 `java -jar backend/target/xxx.jar`
> → `<项目根>/.jwt-secret`。两种方式会生成**两份不同的密钥**，互相不认对方的令牌
> （表现为「换了个启动方式，登录态就没了」）。
> 团队协作/生产部署请用 `-Dmesmax.jwt.secretFile=<绝对路径>` 或环境变量固定下来。

> ⚠️ **`run.cmd` 的内容刻意保持纯 ASCII**（`run.sh` 由 bash 执行，不存在这个问题，照常使用中文注释）。
> cmd.exe 按当前 OEM 代码页（中文 Windows 上是 GBK）解析 `.cmd` 文件，
> UTF-8 中文注释会被按 GBK 解码、丢失字节对齐，把下一条命令的首字符一起吃掉
> —— 实测 `setlocal` 被解析成 `tlocal`，整个脚本失效。中文说明一律写在文档里。

推荐按「车间 → 计划 → 执行 → 质量 → 追溯 → 报表」的顺序演示，每一步都能落到真实数据：

| 顺序 | 页面 | 演示要点 |
|---|---|---|
| 1 | **车间实时看板**（全屏 F11） | 12 台机台状态矩阵实时刷新（SSE），点开一台看实时工况；指出报警机台的红色脉冲与安灯计数 |
| 2 | 设备监控 | 选一台数控车床，看「实时趋势（2 秒）」与「历史趋势（30 秒落库）」两条时间尺度，以及单机 OEE 与目标差距 |
| 3 | 生产订单 | 展示 34 张工单的优先级评分、工序进度；对一张工单做**齐套检查** |
| 4 | 生产排产 | 点「一键自动排产」，看甘特图重排；讲清「加权优先级 + 最早空闲机台」的算法；双击任务块手工调整 |
| 5 | 车间报工终端 | 切到一台有空任务的机台，演示**开工时程序号校验**（故意填错 → 被拒绝），再正常报工，看数量三级联动 |
| 6 | 质量检验 | 打开一张**首件检验单**，修改实测值使其超差 → 判定为不合格；再讲四态闭环处置（含让步接收） |
| 7 | SPC 过程控制 | 切到 MC-005 的外圆直径，看 I-MR 控制图、Cp/CpK 与改善建议 |
| 8 | 刀具管理 | 找一把寿命 97.8% 的刀具，演示「寿命预警 → 卸刀 → 刃磨复位」闭环；点「追溯」看这把刀加工过的工件 |
| 9 | 谱系追溯 | 正向：选一个序列号看全过程链（机床/程序/刀具/批次/操作工）；反向：用刀具或毛坯炉号反查受影响工件 |
| 10 | 统计报表 | 收口：OEE 三级分解（整体→工作中心→机台）、停机帕累托、人员工时与产出 |
| 11 | 系统管理 | 展示角色权限（切 `operator` 账号访问主数据会被 403 拒绝）与操作日志留痕 |

**答辩加分点**（技术深度）：程序号防错、定额快照、四态处置含让步接收、I-MR 而非 Xbar-R 的取舍理由、
SSE 而非 WebSocket 的取舍理由、自研工业控件而非通用组件库的理由 —— 每一条都在文档里有依据。
