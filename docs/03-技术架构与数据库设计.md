# 三、技术架构与数据库设计

## 1. 技术选型与理由

| 层次 | 选型 | 版本 | 选择理由 |
|---|---|---|---|
| JDK | OpenJDK | 17 | Spring Boot 3 的最低要求，也是当前企业主流 LTS |
| 后端框架 | Spring Boot | 3.2.5 | 生态成熟、招聘面广；内嵌 Tomcat，单 jar 即可部署到车间服务器 |
| 持久层 | MyBatis-Plus | 3.5.7 | 中国制造业项目的主流选择；`BaseMapper` + `QueryWrapper` 让主数据的 CRUD 几乎零代码 |
| 数据库 | H2 / MySQL 8 | 2.2 / 8.0 | H2 文件模式用于「零依赖开箱跑」，MySQL 用于生产 |
| 鉴权 | 自研 JWT（HMAC-SHA256） | — | 车间内网部署，鉴权需求极简；少一个依赖就少一份离线升级的麻烦 |
| 实时推送 | SSE | — | 只需服务端 → 大屏单向推送；浏览器 EventSource 原生断线重连 |
| 前端框架 | Vue 3 + Vite | 3.4 / 5.4 | 组合式 API 适合把「工业控件」抽成可复用组件 |
| 图表 | ECharts | 5.5 | 仪表盘/甘特/SPC 控制图/帕累托图开箱即用，且完全离线 |
| UI 体系 | **自研 `ind-*` 设计系统** | — | 刻意不使用通用组件库，见 [工业化 UI 设计规范](04-工业化UI设计规范.md) |

### 1.1 为什么不用 XXX

| 候选 | 不采用的原因 |
|---|---|
| Element Plus / Ant Design Vue | 视觉语言是「互联网后台」，与车间 HMI 差距过大；改主题也改不掉交互习惯（如宽松行高、大圆角） |
| Spring Security | 本系统只有「登录 + 角色模块白名单」两级需求，引入完整安全框架带来的配置复杂度不划算 |
| Redis | 实时态放在 JVM 内存（`MachineStateRegistry`）已足够；单车间 12~60 台设备的数据量不需要缓存中间件 |
| WebSocket | 看板是单向推送，SSE 更简单且自带重连；引入 WebSocket 需要额外处理心跳与协议 |
| Web 字体 / 图标库（iconfont） | 车间内网常常无外网，字体与图标包缺失会直接毁掉界面；因此图标全部内联 SVG、字体用系统栈 |

## 2. 部署架构

```
                   车间大屏（浏览器全屏）
                          │
   办公电脑 / 触屏一体机 ──┤ HTTPS / HTTP
                          ▼
                ┌───────────────────┐
                │  Nginx（前端静态）  │  ← Vue 构建产物；/api 反向代理
                └─────────┬─────────┘
                          │ /api（SSE 关闭缓冲）
                ┌─────────▼─────────┐
                │ Spring Boot 后端   │  :8080/api
                │  · 业务服务         │
                │  · 采集模拟/网关入口 │──▶ 设备网关（FOCAS/OPC UA/MTConnect/MQTT）
                └─────────┬─────────┘
                          │
                ┌─────────▼─────────┐
                │  MySQL 8 / H2      │
                └───────────────────┘
```

单机部署（车间服务器一台）即可满足 60 台机床以内的车间；
采集模拟器与业务服务同进程运行，接入真机时把模拟器换成网关写入即可（见 3.3）。

### 3.1 一个关键设计：BaseCrudController 的钩子而非覆写

通用基类里写了 `save(@RequestBody T entity)`。**子类不能覆写它**：
泛型擦除后父类方法签名是 `save(Object)`，子类写 `save(ProdOrder)` 只是**重载**，
会导致同一路径注册两个处理器而启动失败。因此子类通过钩子注入业务规则：

```java
@Override protected void beforeSave(ProdOrder order) { /* 生成单号、带出工艺路线 */ }
@Override protected String saveMessage() { return "工单已保存"; }
```

这类「泛型 + Spring MVC」的坑在通用基类设计里非常常见，写在这里备忘。

### 3.2 状态机集中建模

工单与工序任务的状态不在各处 `if` 里散落，而是集中为两组枚举（前端 `utils/status.js` 同步维护中文名与色调）：

```
订单：RELEASED 已下达 → SCHEDULED 已排产 → IN_PROGRESS 生产中 → FINISHED 已完工
                     ↘ HOLD 已挂起 ↗            ↘ CANCELED 已取消
工序：PENDING 待派工 → DISPATCHED 已派工 → RUNNING 加工中 → FINISHED 已完工
                                          ↘ PAUSED 已暂停
                                          ↘ INSPECTING 检验中（首件/终检未判定）
设备：RUN 运行 ⇄ IDLE 待机 ⇄ STOP 停机 ⇄ ALARM 报警；MAINT 保养中；OFFLINE 离线
```

### 3.3 设备采集的可替换设计

`MachineSimulator` 是本系统为「没有真实机床」准备的替身，但它复刻了 CNC 的真实行为特征：
主轴转速随状态在额定 45%~95% 波动、进给倍率常见 80/90/100/110/120 档、
坐标持续变化、报警码采用 FANUC/西门子风格（SV0432、SP1245、ALM401…）。

接入真机时**只需替换 `tick()` 的数据来源**：

| 数控系统 | 网关方式 | 可采集量 |
|---|---|---|
| FANUC | FOCAS2 | 运行状态、主轴转速/负载、程序号、刀号、报警码、计数 |
| 西门子 828D/840D | OPC UA | 同上 + 轴坐标、进给倍率 |
| 马扎克 / 通用设备 | MTConnect | 状态、程序、执行时间 |
| 老旧设备（广数、汉奇、HL） | MQTT 采集盒 / IO 点位 | 运行/停机、计数 |

`MachineStateRegistry`（内存实时态）与 `SseService`（推送）保持不变。

### 4.2 关键字段设计

**`md_machine`（机床）** —— CNC 行业的特征字段都在这里：

| 字段 | 含义 | 为什么重要 |
|---|---|---|
| `cnc_type` | 立式/卧式/五轴加工中心、数控车床、车削中心、磨床、线切割、电火花 | 排产时按设备类型匹配工序 |
| `controller_type` | FANUC 0i-MF / SIEMENS 828D / MAZATROL / GSK 980TDi … | 决定用哪种协议采集 |
| `protocol` | FOCAS / OPCUA / MTConnect / MQTT | 采集网关的驱动选择 |
| `max_spindle_speed` | 额定最高转速 | 实时转速条的刻度上限（看「开到几成」） |
| `tool_magazine_capacity` | 刀库容量 | 刀位管理基础 |
| `oee_target` | 单机 OEE 目标 | 报表里直接算差距，而不是所有人共用一个目标 |

**`md_routing_step`（工艺路线工序）** —— 本系统区别于通用 MES 的地方：

| 字段 | 含义 |
|---|---|
| `setup_time` | 准备工时（分钟/批次） |
| `piece_time` | 单件工时（分钟/件）→ 这是 OEE 里「理论节拍」的来源 |
| `nc_program_no` / `nc_program_ver` | **NC 程序号与版本**：报工/开工时与实际执行程序比对，防止程序错版批量报废 |
| `tool_requirement` | 刀具要求（如 `φ12 四刃立铣刀 + M12 螺旋槽丝锥`） |
| `is_key_proc` | 关键工序：完工前必须出首件结论 |

**`prod_order_step`（工单工序任务）** —— 定额与程序号在此**快照**：
工艺路线后续修改不会影响已在制的工单，这是 industry4.0-mes 三层定额体系的核心思想。

**订单完工数量的语义**：`prod_order.finished_qty` = **最后一道工序（seqNo 最大）的完工数**，
即真正的成品产出数。早先取「各工序完工数的最大值」，等于用最领先那道工序的产量冒充成品，
多工序订单的完成率会系统性偏高。列表与看板上的**进度**另行使用「工序完成度」
（stepDone / stepCount，字段 `progress`），数量口径单独放在 `qtyProgress`。

**`prod_machine_telemetry`（设备遥测）** —— CNC 特有量：
`spindle_speed` 主轴转速、`feed_rate` 进给、`feed_override` 进给倍率、
`spindle_load` 主轴负载、`axis_x/y/z` 各轴坐标、`program_no` 程序号、`tool_no` 刀补号、
`alarm_code` 报警码、`run_state` 运行状态、`part_count` 计数、`power_kw` 功率、`coolant_on` 冷却。
索引 `(machine_id, ts)` 支撑趋势查询。

**`trace_log`（过程追溯）** —— 一条记录 = 「某序列号的某道工序，在某台机床、由某人、
用某把刀、按某个程序、加工了多久」，`param_json` 存放切削参数快照。

### 4.3 指标口径（与车间实际管理一致，而不是教科书理想口径）

**OEE**

```
时间开动率 = 实际加工时间 /（实际加工时间 + 停机时间）
性能开动率 = 理论节拍时间 / 实际加工时间，理论节拍 = Σ(单件工时定额 × 报工数量)
合格率     = 合格数量 / 报工总数
OEE        = 时间开动率 × 性能开动率 × 合格率
```

**口径的唯一实现**：`com.mesmax.report.OeeService`。
`/machine/{id}/oee`（单机）与 `/stats/oee`（整体 / 按机台 / 按天 / 按工作中心）都调用它，
不允许任何接口再自己写一套公式 —— 指标只要有两份实现，迟早会互相打架
（曾经单机那版把性能开动率写死成 92%，与报表结论对不上）。

**缺失数据不编数**：某区间取不到工时定额时，性能开动率与 OEE 返回 `null`（前端显示 `—`），
并用 `theorySource: norms | missing` 标明来源。指标缺失要能被看见，不能被「看起来合理」的数掩盖。

**报工记录的两类行**：`prod_task_report.report_type = '开工'` 是**开工占位行**，
数量与工时必须为 0；所有统计（产量、合格率、OEE、工序累计）只累加 `报工/完工` 行，
判断入口统一放在 `OeeService.isProductionRow()`。

**SPC**（I-MR 控制图）

```
移动极差 MRᵢ = |xᵢ - xᵢ₋₁|，MR̄ = 平均移动极差
σ ≈ MR̄ / d₂（n=2 时 d₂ = 1.128）
UCL = X̄ + 2.66·MR̄，LCL = X̄ - 2.66·MR̄
Cp  = (USL - LSL) / (6σ)
CpK = min((USL - X̄)/(3σ), (X̄ - LSL)/(3σ))
```

分级：CpK ≥ 1.67 优 / ≥1.33 良 / ≥1.0 一般 / <1.0 不足，并给出对应的改善建议
（核查刀补磨损补偿周期、缩短换刀间隔、复核装夹定位面与切削参数）。

**设备可靠性**

```
MTTR = 总停机时长 / 故障次数      （修得快不快）
MTBF = 累计运行时长 / 故障次数    （坏得勤不勤）
```

### 4.4 演示数据的确定性生成

业务流水不写在 SQL 里，而由 `DemoDataInitializer` 用固定种子 `20260921` 生成：

```
36 张工单 → 210 道工序任务 → 派工单 → 报工记录
→ 停机记录 → 状态日志 / 遥测历史（近 8 小时 × 5 分钟粒度）
→ 检验单 + 检验项 → 不合格品单 → SPC 采样 → 序列号 × 全过程追溯记录
→ 刀具使用/刃磨/对刀记录 → 点检记录/故障台账/保养工单 → 安灯呼叫
```

工单的计划窗口刻意分成两类：**每 5 张取 2 张**落在「今天之前 0~2 天开工」，
使其计划窗口横跨当前时刻，从而在演示时车间始终保持约 10 台机台处于「加工中」；
其余工单分散在过去 13 天到未来 6 天，形成已完工、在制、待排产的完整时间轴。

这样做的好处：报工数量能对上工序任务与订单数量、追溯记录一定引用真实存在的
机床/程序/刀具/批次、停机能归因到当时在制的工单 —— 手写 SQL 几乎必然出现对不上的数据。
