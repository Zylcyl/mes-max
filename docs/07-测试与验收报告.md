# 附：第二轮复审与修复（16 项定向验证全部通过）

第一轮交付后由独立复审提出了一批问题。逐条核对代码后，**确认大部分成立并已修复**；
其中一条的**成因判断与复审结论不同**（见 1.1），修正后的修法也随之不同，这里如实记录。

## 1. 数据正确性

### 1.1 报工数量翻倍 —— 确认存在，但成因不同 ⚠️

复审判断成因是「`DemoDataInitializer` 写的『开工』记录带着数量，被 `sumByStep` 重复累加」。
核对后确认**两件事都存在，但主因是另一处**：

```java
// 修复前 ProductionService.reportWork
reportMapper.insert(r);                                     // ① 本次报工已经落库
double totalFin = sumByStep(step.getId(), "qty") + qty;      // ② 再把本次数量加一遍
```

`sumByStep` 统计的是该工序下**全部**报工记录，而 `insert` 已在它之前执行 ——
真正触发翻倍的是「先落库、再手工累加」。实测复现：报工 10 件 → 工序累计 20 件。
演示数据里「开工」记录带数量是**同一类问题的第二个隐患**（同样会被重复计入），一并修掉。

**修复**：

| 位置 | 修改 |
|---|---|
| `ProductionService.reportWork` | 改为以库为准：`totalFin = sumByStep(stepId,"qty")`，不再 `+ qty` |
| `ProductionService.sumByStep` | 增加 `ne("report_type","开工")`，开工占位行不参与统计 |
| `DemoDataInitializer` | 新增 `emptyReport()`：开工记录数量/工时一律为 0；汇总同样排除开工行 |

**验证**：报工 10 件后工序累计差额 = 10（修复前为 20）；库中开工记录数量与工时均为 0。

### 1.2 单机 OEE 是假数、且与报表接口打架 —— 确认存在

```java
double perf = 0.92;                 // 硬编码，且 run 未排除开工记录
double oeeValue = availability * perf * quality;
```

**修复**：抽出口径唯一来源 `report/OeeService`，`/machine/{id}/oee` 与 `/stats/oee`
共用同一份公式与同一组取数规则。理论节拍一律取工艺定额（`Σ 单件工时 × 报工数量`）；
**定额缺失时性能开动率与 OEE 返回 `null`（前端显示 `—`），不再编一个看起来合理的数**，
并用 `theorySource: norms|missing` 标明来源。

**验证**：同一台机两个接口的四个指标完全一致（`avail=61.1 / perf=92.5 / qual=100 / oee=56.5`）。

### 1.3 订单完成率虚高 —— 确认存在

`order.finished_qty` 原为「各工序完工数的最大值」，等于用最领先那道工序的产量冒充成品数。

**修复**：改为**最后一道工序（seqNo 最大）的完工数** —— 走完工艺路线才是成品；
列表与看板的「进度」改用**工序完成度**（stepDone/stepCount），数量口径另以 `qtyProgress` 给出。

**验证**：`/stats/output` 完成率 30.1%（不再虚高）；工单列表同时返回 `progress=50%`（工序）与 `qtyProgress=0%`（成品）。

### 1.4 SPC 取最旧样本 —— 确认存在

`/spc/analyze` 用 `orderByAsc` 取最旧 200 条，样本超 200 后**新的超差样本永远进不了控制图**。
**修复**：改为按时间倒序取最近 200 条并在内存中重新升序。
**验证**：分析与序列接口的末点样本号与实测值一致。

## 4. 令牌密钥的「重启后是否要重新登录」（复审提出的决策点）

复审指出：`run.cmd` 未设置 `MES_JWT_SECRET`，意味着每次重启都会让人重新登录。
这是真的，而且是个需要明确取舍的决策，不是可以糊过去的细节。

**最终方案**：把密钥解析放进后端（`JwtUtil.resolveSecret`），顺序为
`环境变量` → `工作目录 .jwt-secret 文件` → `随机生成并落盘`。
既不留固定密钥进版本库，也不会每次重启把人踢下线；无论用 `mvn`、`java -jar` 还是 IDE 启动行为一致。

**验证（真实重启，三次启动 PID 互不相同）**：

```
1) 启动前 .jwt-secret 存在？ false
2) 首次启动（PID 48196）后 .jwt-secret 自动生成？ true（密钥长度 44）
3) 登录取得令牌 → /auth/profile → HTTP 200
   已停止本次启动的后端进程（PID 48196）
   重启为新进程 PID 12480（与上次不同：true）
4) 重启后同一个令牌访问 /auth/profile → HTTP 200
   ✓ 令牌跨重启仍然有效，不需要重新登录
5) 以环境变量 MES_JWT_SECRET 启动后，旧令牌 → HTTP 401
   ✓ 环境变量优先；密钥变化后旧令牌按预期失效
6) 新密钥下重新登录再访问 → HTTP 200
```

> 脚本里刻意加了「启动前断言 8080 已释放」这一步：第一次跑时它直接报错退出，
> 因为旧实例还占着端口，所谓「重启」其实是空转 —— 不加这个断言，
> 就会得到一份看起来很漂亮、实际什么都没验证的结果。

**顺带修掉一个启动脚本问题**：`run.cmd` 加入中文注释后整个脚本解析失败
（`setlocal` 被吃掉首字符变成 `tlocal`）—— cmd.exe 按当前 OEM 代码页（中文 Windows 为 GBK）
解析 `.cmd`，UTF-8 中文会丢失字节对齐。现在 **`run.cmd` 保持纯 ASCII**（已校验：非 ASCII 字节 = 0），
中文说明全部移入文档；`run.sh` 由 bash 执行不受此限制，保留中文注释。

## 1. 修复前复现到的真实缺陷

### 1.1 已完工的工序还能继续开工、报工 ✅ 已修

对一张 `FINISHED` 的派工单再调 `/terminal/start`，修复前返回 200「已开工」；


## 5. 已知限制（本轮未改，需与论文口径一致）

| 项 | 说明 |
|---|---|
| 运行时不会自动生成序列号 | 序列号级追溯依赖种子数据或外部导入的 SN；新建工单在派工/报工阶段不会自动铸造 SN，追溯记录因此只覆盖已有 SN 的工单 |

| H2 仅用于演示 | 生产请用 `mysql` profile；H2 控制台只在 `h2` profile 下装配且仅本机可访问 |
| 仓库未纳入版本管理 | 项目目录下没有 `.git`（`.gitignore` 已备好）——建议交付前 `git init` 并做一次可追溯的提交 |
